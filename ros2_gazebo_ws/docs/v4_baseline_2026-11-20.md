# v4 仿真基线与采摘迁移

2026-11-20，Asia/Shanghai。当前地图为 `/data/tomato_gazebo/gazebo_migration/tomato_corridor_v4.world`。原地图未修改。机械臂安装偏航保持 **180°**，用于避开场景相机。旧 `single_plant_verify_phase3.world` 的车身姿态、RGB、剪切失败和识别结果为历史记录，不能作为 v4 证据。

## 复现静止装配

```bash
cd /data/tomato_gazebo/ros2_gazebo_ws
./verify_v4_baseline.sh

# 打开交互窗口
source /opt/ros/humble/setup.bash
source .overlay/install/local_setup.bash
export ROS_LOCALHOST_ONLY=1 ROS_DOMAIN_ID=93
export GAZEBO_MASTER_URI=http://127.0.0.1:11683 GAZEBO_IP=127.0.0.1
ros2 launch tomato_sim_gazebo baseline.launch.py gui:=true
```

`baseline.launch.py` 使用 `src/tomato_sim_gazebo/config/simulation_baseline.json`。默认静止工位 rail=0.30 m、lift=0 m。Gazebo 在工作区 `validation/runtime_worlds` 读取只加入 `gazebo_ros_state` 的副本。记录源世界路径和 SHA-256；地图轨道、盆、植株与坡度未移动。8 m 轨道的外宽 0.55 m、轨顶 0.040 m，轮轨运动由原 X 轴 `machine_slide` 约束实现。当前关节行程仍是 ±2.5 m，不能把 8 m 视觉轨长当成已验证的全行程。v4 的种植支架沿 X 有坡度，轨道不随支架倾斜；`chassis_cad_datum` 的 π 横滚是 CAD 轴转换，验证车身水平应读 `robot_carriage`。

`validation/v4_baseline/<运行标识>/summary.json` 和 `status.txt` 记录实测，`dependencies.json` 与 `world.json` 记录依赖和实际启动的世界；`gazebo_v4_robot_overview.png` 来自独立 Gazebo 诊断相机，`gazebo_v4_rgb.png` 来自 `/camera/color/image_raw` 的右侧作业相机，两者均记录世界、话题和帧时间。此验收只证明整机在 v4 装配工位静止稳定、轨道实体存在、Gazebo RGB-D 正常发布。

目录重构前的静止装配实测结果为 **PASS**。通过 `/get_entity_state` 直接读取 Gazebo 中的车体承载链节，其横滚、俯仰均小于 `10⁻⁶°`，中心位于 `Y≈0`、轨顶 `Z=0.040 m`。约 1.95 s 的静止采样中，六轴相对 OEM 初始位的最大误差约 `0.00018 rad`，轨位约 `0.30000015 m`。Xacro 及运行时 `robot_description` 均确认机械臂安装偏航为 `180°`。

## Phase 3 / 4 使用的 v4 采摘副本

`scripts/prepare_phase3_world.py` 默认从 v4 原图生成 `validation/phase3/tomato_corridor_v4_phase3.world`。94 个原有 include 的位姿保持原值，60 株仍在原位。取 `plant_0_8_1`（模板 `corridor_v4_plant_s0_i7`）的 `9_1` 为第一轮试验目标，将该株四串拆为独立顶层实体，恢复 `9_1` 源 SDF 中的精细果梗碰撞。保留 v4 本身已有的主茎网格和果球碰撞，不移动盆、支架或轨道。目标剪切点由原 v2 植株局部坐标变换到该 v4 实例，世界坐标约 `[1.19991, -0.71302, 2.07548]` m。每株主茎有独立接触报告，避免其它植株的空消息盖掉正在发生的接触。切点距离、刀口接触、槽内范围和主茎门禁保持旧规则。

`scripts/audit_v4_harvest_world.py` 比对源文件与生成 SDF，检查 59 个非目标实例几何、94 个原有 include 位姿及目标拆分前后的几何，允许旧规则指定的跨剪切平面连接球移除。它曾定位到 SDF 圆柱轴转换的符号错误，已修正。`validation/v4_harvest_world_audit.json` 是几何审查结果，`gz sdf -k` 是格式检查，均不代表剪断通过。

v4 目标高度明显不同于旧单株场景。rail=1.25 m、lift=0.50 m、右侧相机偏角 32°、仰角 25° 是当前候选采摘工位参数，可在验证脚本用环境变量覆盖。离线 KDL 测试只能说明部分进刀姿态可解，不能代替物理接近轨迹、相机果梗识别、携果和入筐验收。尤其固定升降台调高之后必须重验 `basket_link` 上方出筐路点。

## 真机代码复用边界

`xc_robot_main_control_node` 和 `yolov8_service` 直接从真机工作空间导入。主控继续负责接收视觉、计算剪切点和进刀姿态、驱动原有 ROS 服务和采摘状态机。视觉使用原用户模型 `tomato-seg2025063018-yolov8-xucan.pt`，没有替换检测算法。仿真分别使用系统 ROS Python 兼容的 `.venv_ros` 与继承 `tomato_sim` 的 `.venv_yolo`，使用原生 `cv_bridge`，主控使用原生 `pyrealsense2` 反投影。

为直接运行原节点，真机主控源码增加了保留硬件默认值的 ROS 参数、可选 MoGe 延迟导入、相机进程管理开关和服务未就绪时的重试；YOLO 源码增加请求日志和退出清理。Gazebo 供给 1 mm 单位的对齐深度及按实际 TF 生成的手眼矩阵，运行真机 RGB-D 分支。适配层替代了真机 AUBO SDK 驱动、夹爪控制器、AGV、相机硬件驱动与腕部输入信号；AUBO 真机 C++ 运动服务、腕部分类节点没有直接跑在当前 Gazebo 采摘链路中。`vision_pose_generate` 被构建，当前固定工位链路不使用它的二阶段视觉服务。
